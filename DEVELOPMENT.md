# Локальный запуск и сборка сайта

Для локального просмотра нужен установленный Python. Откройте PowerShell в папке проекта и выполните команды по очереди:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m mkdocs serve
```

Первые две команды подготавливают окружение и устанавливают необходимые компоненты. Последняя запускает сайт. Откройте в браузере [http://127.0.0.1:8000/](http://127.0.0.1:8000/). Чтобы остановить сайт, нажмите `Ctrl+C` в окне PowerShell.

Перед публикацией изменений выполните проверку и сборку:

```powershell
.\.venv\Scripts\python.exe -m mkdocs build --strict
```

Готовый сайт появится в папке `_site`. Если при сборке обнаружатся ошибки или предупреждения, их нужно исправить перед публикацией.

## Публикация в Cloudflare Workers

Сайт руководства размещён в Cloudflare Workers:
[gisogd-user-guide.polakov1245.workers.dev](https://gisogd-user-guide.polakov1245.workers.dev/).

GitHub хранит исходники и проверяет изменения. Workflow `Documentation checks`
собирает сайт на push в `main`, при создании pull request и по ручному запуску.
Готовые файлы сохраняются как артефакт проверки; сам workflow сайт не публикует.

Публикация выполняется в проекте `gisogd-user-guide` в Cloudflare. В настройках
сборки этого проекта указаны следующие значения:

| Параметр | Значение |
|---|---|
| Репозиторий | `DmiBear/gisogd-user-guide` |
| Ветка | `main` |
| Корневая папка | `/` |
| Команда сборки | `./build.sh` |
| Команда публикации | `npx wrangler deploy` |
| Папка готового сайта | `_site` |

Файл `wrangler.jsonc` связывает команду публикации с Worker `gisogd-user-guide`
и папкой `_site`. Адрес в `mkdocs.yml` должен совпадать с опубликованным адресом сайта.
Новый проект Cloudflare для этих изменений создавать не требуется.

Для запуска `./build.sh` в Linux файл должен сохраняться в Git как исполняемый
с режимом `100755`. Правило в `.gitattributes` сохраняет для него переносы строк LF.

Перед отправкой изменений выполните проверки:

```powershell
.\.venv\Scripts\python.exe tools/check_publication.py
.\.venv\Scripts\python.exe -m mkdocs build --strict
```

После отправки в `main` проверьте результаты GitHub Actions и сборки Cloudflare
отдельно. Если автоматические сборки Cloudflare включены, новая отправка в эту ветку
запустит обновление сайта. В разделе **Deployments** убедитесь, что этап публикации
завершился успешно, затем откройте сайт и проверьте изменённые страницы.

Успешная проверка GitHub Actions подтверждает сборку, но не подтверждает публикацию.
Если сборка Cloudflare завершилась с ошибкой, найдите в журнале первую строку ошибки
после запуска команды сборки или публикации.
## Проверки содержания и интерфейса

Перед публикацией выполните из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tools -p "test_*.py"
node --test tools/test_lightbox.cjs
.\.venv\Scripts\python.exe tools/check_publication.py
.\.venv\Scripts\python.exe -m mkdocs build --strict
.\.venv\Scripts\python.exe tools/check_docs.py
```

Для тестов окна рисунков нужен Node.js 24. В проверках GitHub Actions он устанавливается отдельно; сборка сайта остаётся на MkDocs.

`check_docs.py` проверяет локальные ссылки и якоря готового сайта, полноту меню, порядок рисунков 1–150 и соответствие снимков файлу `evidence/media-manifest.json`. Старые адреса объединённых страниц и их закладки сохраняются через страницы-обзоры.

Новые или заменённые рисунки согласуйте с текстом и обновите сведения в манифесте. Не обновляйте контрольные суммы только для того, чтобы убрать ошибку проверки. Неизвестная версия интерфейса отмечается как `null`; дата редакции руководства не подтверждает проверку приложения.

Автоматические тесты не заменяют просмотр сайта: проверьте главную страницу на узком экране, обе темы, поиск и открытие рисунка мышью и клавиатурой. После закрытия рисунка должны сохраниться место чтения и фокус.

Главная страница оформляется как оглавление технического руководства с прямыми ссылками на операции и все 18 реестров. Не добавляйте рекламные карточки, призывы и ссылки на личное портфолио в страницы руководства. Реальные названия элементов системы, включая «Популярные разделы», сохраняйте без редакционной подмены.
